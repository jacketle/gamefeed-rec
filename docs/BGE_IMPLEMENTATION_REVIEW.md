# BGE实现核查与报告用语说明

核查日期：2026-11-02。核查代码是 `scripts/audit_semantic.py`，实测结果保存于 `reports/release/semantic_audit/audit.json`。本次对照使用开发集，原测试集结果保持原样。

## 1. 官方到底提供了什么

**KuaiRand官方提供数据和字段说明。** 我查阅了官方主页、数据论文和数据仓库，没有找到“BGE编码文案＋历史向量取平均”这套方法的官方推荐结果。文案补充表提供视频文案、封面文字，类别补充表提供类别名称；通过 `final_video_id` 与视频编号连接。它们是模型输入材料。

**BGE官方提供文本编码器和使用示例。** 当前项目使用 `BAAI/bge-small-zh-v1.5`，中文小模型，输出512维向量。官方支持 `SentenceTransformer` 加载；底层取CLS位置的输出，再将向量长度归一化为1。此时两个向量的点积就是余弦相似度。CLS是文本开头的特殊位置，用来提取整段文本的表示。

官方v1.5说明允许不加查询指令；短问题查长文章时建议比较加指令的效果。当前方案比较的是视频文案，不能因为没加指令就认定实现错误。

来源：[KuaiRand主页](https://kuairand.com/)、[数据论文](https://arxiv.org/abs/2208.08696)、[数据仓库](https://github.com/chongminggao/KuaiRand)、[BGE官方模型说明](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[官方CLS配置](https://huggingface.co/BAAI/bge-small-zh-v1.5/blob/main/1_Pooling/config.json)。

## 2. 我们的代码怎样推荐视频

`src/gamefeed/text_retrieval.py` 实际执行：

1. 把视频文案、封面文字、类别文字拼接起来。
2. 用BGE生成每个视频的512维向量，归一化后保存。
3. 找到用户前一天结束前最近20条观看达标记录。
4. 对这些视频向量取平均，再归一化，作为用户兴趣向量。
5. 与当天可用视频逐个计算点积，按分数取前100条。
6. 没有历史记录时使用热门列表。

步骤2采用BGE官方支持的编码方式；步骤3到6是本项目的推荐设计。报告统一标为 **BGE＋历史均值**，避免把整套推荐方法的表现归因于一个文本模型。

若用户历史既有游戏又有美食，直接取均值只保留一个综合兴趣向量。可以进一步比较分别保留游戏、美食兴趣的方式，但提升幅度要由实验回答。

这里的128和512是分词后的文本单元数（token），不严格等于汉字数。官方配置支持512，项目为缩短CPU编码时间设置128。

| 开发集对照，全部5,410组 | Recall@100 |
| --- | ---: |
| 原实现：128长度，历史向量平均 | 3.616% |
| 只恢复512长度，其余相同 | 3.622% |
| 128长度，近期历史权重更高 | 3.473% |
| 从当天可用库均匀随机取100条的数学期望 | 1.319% |

近期权重对照沿用ItemCF的形式：最新一条权重1，前一条1/1.1，再前一条1/1.2，以此类推，然后求加权平均。随机一行由候选库大小和正例可用情况计算，属于数学期望，不是另一次模型训练结果。

**判断：低分可以复现，文本长度不是本次低分的主要原因。** 本次也没有发现ID错位、保存向量错误或句向量提取错误。开发集结果说明当前组合超过均匀随机，但明显弱于协同过滤；它衡量“找回当天观看达标视频”的能力，与文本主题是否相似是两个不同问题。

## 5. 报告里的中文名称

### 观看达标：对应long_view

按照KuaiRand官方说明，视频时长不超过18秒时看完才算达标；视频超过18秒时观看至少18秒算达标。这里沿用数据提供的0/1标签。

| 视频时长 | 实际观看 | 观看是否达标 |
| --- | --- | --- |
| 10秒 | 8秒 | 否，标签0 |
| 10秒 | 10秒 | 是，标签1 |
| 60秒 | 17秒 | 否，标签0 |
| 60秒 | 20秒 | 是，标签1 |

官方的“有效播放”还有另一套7秒判断规则，本项目的观看达标使用上面的18秒规则。

### 召回评估样本：同一用户同一天算一组

张三4月25日、张三4月26日、李四4月25日是三组。每组使用截至前一天的历史；当天观看达标的不同视频作为要找回的正例。一组返回100条视频，计算找回多少正例，再对所有组取平均。只评价当天至少有一条正例的组。

因此7,122组不等于7,122名用户，也不等于7,122次真实推荐请求。它是我们为了离线评价采用的分组方式。正文用“按用户和日期分组的评估样本”，图中在已解释定义后简写为“评估样本”。代码中的原始字段和文件名保留，避免破坏数据接口。

### 其他图表名称

- 正例召回率 Recall@100：每组当天观看达标的视频有多少进入前100条，随后求各组平均。
- 至少命中一条的比例 HitRate@100：前100条命中至少一个正例的组数，占全部评估组数的比例。
- 内容覆盖率：所有推荐结果出现过的不同视频数，除以7,583。
- AUC：正例得分高于负例的能力，分别评价观看达标和点赞两个任务。
- BGE＋历史均值：预训练文本模型加上本项目的平均历史向量方法。
